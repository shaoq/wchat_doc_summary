## Context

`sector-group-tracking` 已经提供分组、成员、建议和组级趋势报告能力。当前建议生成主要依赖近期板块共现；当 CLS 看盘数据没有结构化 `sectors` 标签时，系统会退化为基于 `market_sectors` 行情缓存的同日榜单共现。

同日榜单共现只能表示行情线索，不能证明板块属于同一产业链或主题。它容易把宽带提速、猪肉、CRO、国产软件等无关方向聚在一起，导致 `groups suggestions` 展示低质量分组。

本次变更的核心是把建议生成从“共现即分组”改成“规则候选 + 主题约束 + AI 语义清洗 + pending 审核”。

## Goals / Non-Goals

**Goals:**

- 降低跨主题误聚类，避免将语义无关板块放入同一产业链建议。
- 保留 `market_sectors` 作为 CLS 缺失时的线索来源，但降低其置信度并增加约束。
- 引入内置主题词典，覆盖当前数据中高频且语义明确的方向。
- 引入 AI 对候选聚类做结构化语义清洗，剔除误入成员并生成更合理的组名和关系类型。
- AI 不可用时仍有可预测的规则兜底，且不得输出明显混杂建议。
- 所有建议仍以 pending 形式落库，用户确认后才影响正式分组。

**Non-Goals:**

- 不实现完整行业知识图谱。
- 不让 AI 自动接受建议或直接修改正式分组成员。
- 不让 AI 凭空添加当前候选池或 tracked sectors 中不存在的板块。
- 不改变 `groups accept`、`groups ignore`、`groups add` 的基本交互语义。
- 不要求第一阶段覆盖所有 A 股概念板块，只覆盖当前数据中明显可分类的主题。

## Decisions

### 1. 建议生成拆成四段流水线

选择：

```text
collect inputs
  -> build rule candidates
  -> apply theme constraints
  -> semantic clean with AI
  -> persist pending suggestions
```

理由：

- 规则候选负责召回，AI 负责清洗和命名，二者职责分离。
- 可在 AI 失败时保留规则高置信建议。
- evidence_json 可以记录每段决策依据，方便用户审查。

替代方案：

- 让 AI 直接从全部候选板块生成分组。放弃原因：成本高、不可复现、容易引入不存在的板块。
- 只用规则词典不接 AI。放弃原因：词典覆盖有限，无法处理新主题和边界成员。

### 2. 内置主题词典作为第一道语义约束

第一阶段内置主题可覆盖：

```text
光伏产业链:
  光伏, TOPCon, BC电池, HIT电池, 钙钛矿

锂电储能链:
  锂电池, 固态电池, 钠电池, 电解液, 盐湖提锂, 锂矿, 充电桩

军工信息链:
  卫星导航, 军工航天, 海工装备, 大飞机, 军民融合, 国产软件, 信息安全

医药服务链:
  CRO, CXO, 仿制药, 生物疫苗, 甲型流感, 基因测序

消费农业链:
  猪肉, 鸡肉, 白酒, 水产品

新能源电力链:
  风电, 风能, 核电核能, 地热能, 钒电池, 碳交易
```

主题词典应优先作为候选过滤和命名依据，而不是作为正式分组事实。最终仍生成 pending 建议。

替代方案：

- 将主题词典存数据库。放弃原因：第一阶段需要快速稳定验证，配置化可作为后续增强。

### 3. `market_sectors` 共现只能产生低置信线索

当建议来源是行情缓存同日共现时：

- 置信度上限低于 CLS 结构化板块共现。
- reason 必须说明是“行情缓存同日共现线索”。
- 若不能通过主题词典或 AI 清洗形成单一主题，不能落库为 `new_group`。

理由：

- 同日强弱榜共现反映市场环境，不等价于产业链关联。
- 用户需要知道建议是强语义证据还是弱行情线索。

### 4. AI 语义清洗使用结构化 JSON 合约

AI 输入应包含：

- 候选分组名或规则主题名。
- 候选成员列表及 sector_id、名称、状态、来源、共现分数、主题词典命中。
- 已有分组名称、别名、关键词和成员摘要。
- 明确约束：只能保留输入成员，不能新增板块，不能接受建议。

AI 输出应包含：

```json
{
  "accepted": true,
  "suggested_group_name": "光伏产业链",
  "confidence": 0.82,
  "reason": "成员集中在光伏电池技术路线和设备材料方向",
  "members": [
    {
      "sector_id": 1,
      "relation_type": "core",
      "confidence": 0.9,
      "reason": "光伏为主题核心"
    }
  ],
  "rejected_members": [
    {
      "sector_id": 9,
      "reason": "消费农业方向，与光伏主题无直接关系"
    }
  ]
}
```

AI 返回无效 JSON、低置信、成员不足或违反约束时，系统应丢弃该 AI 结果并使用规则兜底。

### 5. 已有 pending 建议需要刷新而不是重复创建

现有去重语义保持不变。增强后如果同一主题再次生成建议：

- 应刷新 confidence、reason、evidence_json 和成员清洗结果。
- 不应重复创建同名同成员的 pending 建议。
- 被用户 ignored 的关系不应在证据没有实质变化时再次出现。

## Risks / Trade-offs

- [Risk] AI 输出不稳定 -> 通过主题词典预过滤、结构化 JSON schema、成员池约束和低置信拒绝降低风险。
- [Risk] 词典覆盖不足导致漏建议 -> 第一阶段优先减少误报；后续可支持用户配置词典。
- [Risk] AI 调用增加成本和耗时 -> 仅对规则候选聚类调用 AI，并限制候选数量。
- [Risk] AI 不可用导致体验退化 -> 规则高置信建议仍可生成，低质量混杂聚类直接丢弃。
- [Risk] 过度过滤错过行情线索 -> reason 中保留行情共现证据，后续可提供专门的“行情线索”视图，而不是混入产业链建议。

## Migration Plan

1. 复用现有建议表和 `evidence_json`，不新增迁移。
2. 实现主题词典和候选清洗后，新的 `groups suggest` 只影响后续 pending 建议。
3. 已有低质量 pending 建议不会自动接受；用户可手动 ignore，或后续生成时刷新为更干净的建议。
4. 回滚时移除 AI 清洗和主题过滤逻辑，现有正式分组和成员不受影响。

## Open Questions

- 第一阶段是否需要暴露 `--no-ai` 或 `--rules-only` 参数，方便离线/低成本运行？
- 内置主题词典是否放在代码常量、JSON 配置文件，还是后续迁移到数据库？
- `groups suggestions` 是否需要展示被 AI 剔除的成员，还是仅在详细视图/JSON evidence 中保留？
