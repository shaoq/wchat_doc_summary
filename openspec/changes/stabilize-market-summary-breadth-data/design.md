## Context

当前 `market-summary` 的成交额和涨跌统计来自 `FinanceClient` 的全市场股票快照链路。这个链路有三个已经被实测证实的问题：

- 东方财富快照接口的 `data.diff` 已从 `list` 变为按序号索引的 `dict`，现有 `_normalize_stock_snapshot()` 会直接把响应判为空。
- 即使兼容 `dict`，当前单次请求也只返回单页约 100 条样本，而接口同时声明 `total=5518`；直接基于单页样本计算会得到失真的“伪全市场”结果。
- 备用的 `akshare.stock_zh_a_spot_em` 在当前超时和重试配置下经常超时，无法作为稳定兜底。

这导致 CLI 经常展示 `成交额: 已获取 0亿` 和 `涨跌统计: 已获取 0/0/0`。更严重的是，当前零值 contract 会被当作普通结果继续展示和缓存，调用方无法区分“真实零值”和“抓取失败后的降级值”。

## Goals / Non-Goals

**Goals:**
- 让成交额和涨跌统计优先基于可验证的完整全市场快照计算，而不是误用单页片段。
- 为成交额和涨跌统计增加显式质量状态，使 CLI 和缓存层能区分成功、部分成功和失败。
- 避免把降级零值写入缓存，防止错误结果在后续离线/历史场景中持续复用。
- 保持现有 `market-summary` 主流程结构不变，只修正宽度数据链路和展示语义。

**Non-Goals:**
- 不在本次变更中重写全部市场数据源策略。
- 不新增市场总结的数据维度，也不调整 AI 总结模板结构。
- 不实现任意历史交易日的全市场宽度重建。
- 不要求所有市场数据项都引入同等级别的质量元数据，本次范围只覆盖成交额和涨跌统计。

## Decisions

### 1. 以“分页全量快照”替代当前的“单页快照假设”

`EastMoneyCurlClient.get_stock_list()` 将继续作为成交额和涨跌统计的主快照源，但 `FinanceClient` 不能再假设一次请求就能拿到完整市场样本。新实现应：

- 同时兼容 `data.diff` 为 `list` 或 `dict`
- 从首页读取 `data.total`
- 逐页抓取并聚合，直到累计条数达到 `total` 或明确确认上游已无更多数据
- 只在快照条数与 `total` 一致，或满足等价完整性判定时，才视为完整快照

这样可以直接修复当前的结构漂移问题，并避免把单页 100 条样本误当全市场。

备选方案：
- 只兼容 `diff=dict`，继续使用单页结果。放弃原因：虽然能把 `0` 变成非零，但结果仍明显失真。
- 直接把 `akshare.stock_zh_a_spot_em` 升级为主源。放弃原因：当前实测超时明显，主路径稳定性不足。

### 2. 为成交额和涨跌统计引入显式质量状态

仅靠 `{sh_volume, sz_volume, total_volume}` 和 `{up_count, down_count, flat_count}` 这两个 dict，调用方无法判断数据是“真实成功”还是“失败降级”。本次设计要求在市场数据聚合结果中为这两项增加显式质量描述，至少包含：

- `status`: `ok | partial | error`
- `source`: 实际命中的数据源
- `actual_count`: 实际参与计算的股票条数
- `expected_count`: 上游声明的总条数，若可得

其中：

- `ok` 表示来自完整快照或可信备用源
- `partial` 表示只拿到不完整样本，结果可用于诊断但不能当作稳定成功
- `error` 表示主源和备用源均不可用，最终返回零值 contract

备选方案：
- 仅依赖日志区分成功和失败。放弃原因：CLI 和缓存层都需要结构化状态，日志不足以支撑行为分支。

### 3. CLI 展示以质量状态为准，而不是以 key 是否存在为准

`market-summary` CLI 现在只要看到 key 存在就显示“已获取”，这会把降级零值伪装成成功。本次改造中：

- 只有 `status=ok` 时，成交额和涨跌统计才显示“已获取”
- `status=partial` 时，应显示“样本不完整”或等价提示，并可附带样本规模摘要
- `status=error` 时，应显示“获取失败”或“已降级为空值”，不能显示成功措辞

这样可以让用户第一眼就知道问题是在抓取失败、样本不完整还是完整成功。

备选方案：
- 保持原展示，只在 debug 日志补充说明。放弃原因：用户当前就是在 CLI 成功提示下误以为数据已正常获取。

### 4. 缓存只接受 `ok` 的宽度数据

缓存层要避免把错误结果持久化。成交额和涨跌统计写库时应基于质量状态做门控：

- `status=ok` 时允许插入或更新对应表
- `status=partial` 或 `status=error` 时跳过该表写入
- 若同一交易日已有旧的有效缓存，本次无效抓取不得覆盖旧值

这保证离线和历史模式读到的仍是最后一次可信结果，而不是最新一次失败结果。

备选方案：
- 允许写入 `partial`，并通过额外标志位区分。放弃原因：当前缓存 schema 没有质量字段，先把无效结果挡在缓存外更稳妥。

## Risks / Trade-offs

- [分页抓取会增加实时耗时] → 通过单次共享快照复用成交额和涨跌统计，避免重复抓取；收盘后继续依赖缓存降低重复成本。
- [上游 `total` 或分页行为未来可能再次变化] → 解析层同时保留 `list/dict` 兼容，并把“完整性判定失败”转为显式 `partial/error`，而不是静默吞掉。
- [新增质量元数据会影响部分调用方假设] → 保持原有数值 contract 不变，把质量状态放在新增字段中，减少兼容性风险。
- [跳过无效写库后，部分交易日可能缺失宽度缓存] → 这是预期行为，优先避免错误数据污染本地缓存。

## Migration Plan

1. 在 `FinanceClient` 中实现分页全量快照抓取与完整性判定。
2. 为成交额和涨跌统计补充质量状态元数据，并把聚合链路改为基于该状态做后续决策。
3. 更新 CLI 状态渲染逻辑，只在 `ok` 时显示成功语义。
4. 更新缓存写入逻辑，对 `partial/error` 的宽度数据跳过写库，并补回归测试。
5. 跑市场数据 contract、CLI 流程和缓存相关测试，验证 `ok / partial / error` 三类路径。

回滚策略：
- 若分页快照实现引入不可接受的性能问题，可临时回退到旧主源加明确失败展示，但保留 CLI/缓存的状态语义修正，避免继续误报成功。

## Open Questions

- `partial` 展示文案是否统一使用“样本不完整”，还是区分“仅单页样本”“分页中断”等更细粒度原因。
- 是否需要把宽度数据质量状态进一步传递给 AI prompt，用于让总结明确说明“市场宽度数据不完整”；这不在本次必须范围内，但实现时可能值得顺带评估。
