## Context

当前抓取链路中，单订阅默认无范围抓取会走“最新 10 条”模式，批量抓取 `fetch_all()` 也会复用这一路径。该设计适合手动补抓单个订阅，但不适合持续同步多个订阅，因为每个订阅都会至少打一次文章列表请求，即使该订阅没有新文章也一样。与此同时，`fetch_feed()` 在第一页列表为空时会直接停止，`WeReadClient.get_articles()` 对异常格式响应会兜底成空列表，这会把“临时空响应”与“真正没有文章”混在一起。

这次变更跨越 CLI、抓取调度、Provider 响应校验和同步状态记录，属于横切抓取链路的行为修正，值得在实现前固定设计边界。

## Goals / Non-Goals

**Goals:**

- 让 `wchat fetch --all` 默认路径以“尽量不触发限流”为首要目标
- 将批量默认语义收敛为增量同步，减少对无新文章订阅的重复请求
- 避免把可疑空响应误记为成功抓取 `0` 篇
- 为 CLI 和日志提供可解释的抓取结果分类
- 保持显式 `--days` / `--full` 语义不变

**Non-Goals:**

- 不实现限流后的自动恢复或后台调度
- 不引入新的外部缓存、队列或任务系统
- 不改变单订阅默认无范围抓取使用“最新 10 条”的语义
- 不改变 wechat2rss 的数据源协议，只在统一抓取层增加保护

## Decisions

### D1: `fetch --all` 默认无范围抓取改为批量增量同步

批量模式与单订阅模式分离语义：

- 单订阅 `wchat fetch MP_ID` 保持“最新 10 条”
- 批量 `wchat fetch --all` 改为优先调用 `fetch_incremental()`
- 若某订阅本地没有任何文章，再退化到轻量初始化抓取

这样做比“批量也抓最新 10 条”请求更少，也更符合日常同步而非补抓的使用场景。

备选方案：
- 保持批量默认最新 10 条，只增加 sleep。放弃原因：虽然更慢，但仍会对所有订阅固定请求，无法从根上减少无意义访问。

### D2: 主动节流放在 `fetch_all()` 调度层，而不是底层 HTTP 客户端

主动节流需要知道“这是批量模式”“上一个订阅是否异常”“当前是否应加长等待”，这些都是业务层信息，放在 `FetcherService.fetch_all()` 更清晰。底层 `WeReadClient._request()` 仍保留现有请求级重试和限流识别，但不承担批量节奏控制职责。

备选方案：
- 在 `_request()` 内对所有请求统一 sleep。放弃原因：会影响单订阅抓取和其他调用路径，且无法基于订阅级结果做差异化退避。

### D3: 把“第一页空列表”视为可疑状态，执行有限重试后再判定为空

对文章列表抓取增加“可疑空页”语义：

- 第一页或增量第一页为空时，不立即认定无数据
- 在有限次数内以退避方式重试同一页
- 仅在重试后仍为空时，才返回最终空结果

这样可以覆盖临时空响应、代理抖动或异常响应被上游吞掉的场景。

备选方案：
- 所有空页都直接报错。放弃原因：确实存在“真的没有新增文章”的正常空结果，完全报错会让批量同步过于敏感。

### D4: 非法列表响应不再静默归一化为空列表

`WeReadClient.get_articles()` 目前对非 dict 响应兜底返回空列表，这会丢失异常上下文。新设计要求：

- 对无效响应结构抛出明确错误
- 仅对结构合法且文章数组为空的结果，认定为真实空页候选

这样上层才有机会把“异常空”与“真实空”区分开。

### D5: 抓取结果采用分类统计，而不是只返回“新增文章列表长度”

当前 CLI 只展示 `len(articles)`，无法区分“全已存在”和“上游异常空”。新设计要求抓取链路暴露更细的结果摘要，至少覆盖：

- list_returned_count
- inserted_count
- existing_count
- failed_count
- suspicious_empty_retried
- final_state

CLI 基于该摘要输出更精确的结果文案；服务层仍可保留已插入文章列表供调用方复用。

### D6: `sync_time` 只在可确认成功的同步后更新

如果本次抓取最终落在“可疑空响应放弃”或“列表响应无效”状态，不应更新 `feeds.sync_time`。否则用户会看到一次看似成功的同步时间，掩盖异常。

## Risks / Trade-offs

- **[同步更慢]** 批量模式增加等待后，总耗时会显著上升 → 这是目标内 trade-off，优先保稳定性
- **[批量与单订阅语义分叉]** 用户需要理解两种默认行为不同 → CLI 文案中显式标注“批量增量同步”
- **[实现复杂度上升]** 结果统计和空页分类会让返回结构更复杂 → 通过新增摘要结构并保留兼容字段降低侵入
- **[增量基线依赖发布时间]** 个别缺失发布时间的旧记录会削弱增量停止条件 → 保持现有保守策略，并继续依赖后续回填

## Migration Plan

1. 先在服务层引入新的批量调度与结果摘要结构。
2. 再调整 CLI 默认语义与输出文案。
3. 为新旧批量行为补测试，覆盖限流预防、可疑空页、无新增和异常空响应。
4. 如新语义不稳定，可仅回退 `fetch --all` 到旧入口，同时保留响应校验和统计改进。

## Open Questions

- 批量订阅间基础等待和异常退避的默认秒数是否需要暴露为配置项，还是先固定在代码内。
- 对首次初始化订阅，批量默认是抓“最新 N 条”还是“单页增量退化抓取”更符合实际使用习惯。
