## Context

当前 `market-summary` 的市场数据层已经拆分为多源策略，但三类关键信号仍然存在明显的不一致：

- 涨跌统计使用 `pytdx` 主源，能够表达 `ok / partial / error`，但在轻微缺失时不会进一步补抓，也不会尝试把“几乎完整”的结果与“明显不完整”的结果区分开来。
- 涨停股虽然优先使用专用涨停池，但 contract 在归一化阶段被固定裁剪为 20 条，导致数据层天然不是全量。
- 板块 contract 固定为 `top 5 + bottom 5`，这对摘要展示足够，但对盘后总结的输入广度偏窄。

与此同时，缓存层当前只接受 `ok` 宽度结果写入。这保护了缓存不被坏数据污染，但也会让“轻微缺失但足以复用”的统计结果无法沉淀，导致相同交易日重复触发在线抓取并持续抖动。

这次变更是一个跨 `finance.py`、缓存服务、CLI、AI 输入摘要与测试契约的横切升级，因此需要在实施前明确技术决策。

## Goals / Non-Goals

**Goals:**
- 让涨跌统计路径以“尽可能补齐”为优先目标，而不是在首次发现缺失后立即接受 `partial`。
- 将涨跌统计质量状态从粗粒度的 `ok / partial / error` 升级为能区分“近完整”和“明显不完整”的 contract。
- 将涨停股数据层从固定 top-20 改为尽可能保留全量池，同时保留展示层裁剪能力。
- 将板块输入从 `5 + 5` 升级为 `10 + 10`。
- 调整缓存门控，使“近完整”的宽度结果能够复用，同时继续阻止坏数据覆盖已有有效缓存。
- 让 `market-summary` CLI 和 AI 输入摘要能够解释新的质量状态和更大的输入规模。

**Non-Goals:**
- 不改变指数数据源策略。
- 不在本次变更中引入新的第三方依赖或新的外部供应商。
- 不重构整个 `MarketAnalyzer` 聚合流程，只调整其消费到的市场数据 contract。
- 不把“展示多少条涨停股/板块”与“数据层保留多少条”永久绑定为同一件事。

## Decisions

### D1: 涨跌统计保留 `pytdx` 主源，但增加缺失补抓与 `near-complete` 状态

选择：
- 首轮 `pytdx` 批量抓取后，记录未返回有效 quote 的证券。
- 对缺失证券做有限轮次的定向补抓。
- 最终质量状态从三态升级为四态：`ok`、`near-complete`、`partial`、`error`。

理由：
- 当前 `5200/5201` 与 `4800/5201` 都落入 `partial`，信息价值太低。
- 在保留现有主源和 universe 筛选方式的前提下，缺失补抓是成本最低的完整性增强方式。
- `near-complete` 能让系统表达“极少数缺失但结果可复用”，避免轻微缺失长期造成运营噪音。

备选方案：
- 继续沿用三态，只调整 CLI 文案。放弃原因：不能解决缓存和可复用性问题。
- 用 akshare 直接替代 `pytdx` 主源。放弃原因：前一个 change 已经确认统计旧链路不稳定，不适合回退为主源。

### D2: 缓存门控从“仅 ok”升级为“允许 near-complete”

选择：
- `market_volume` 仍仅接受 `ok` 写入。
- `market_statistics` 接受 `ok` 和 `near-complete` 写入。
- `partial` 与 `error` 仍禁止写入，且不得覆盖已有有效缓存。

理由：
- 成交额当前来自交易所官方源或旧链路兜底，质量模型比较明确，不需要引入近完整语义。
- 涨跌统计更容易出现极少量 quote 丢失，因此需要一个可缓存的“足够好”状态。
- 这样可以减少同一交易日重复请求 `pytdx` 带来的不稳定性，同时保留缓存保护语义。

备选方案：
- 宽度两项都统一允许 `near-complete`。放弃原因：成交额没有同等的“少量缺失但仍可接受”语义基础。

### D3: 涨停股 contract 改为“数据层全量，消费层裁剪”

选择：
- 去掉归一化阶段的固定 `limit=20` 上限。
- 主源返回多少就保留多少；兜底源也尽量保留全部候选结果。
- CLI 与 AI 输入摘要可以独立定义展示上限，但不能再反向限制底层 contract。

理由：
- 当前 top-20 是典型的展示层假设，放在数据层会让缓存、测试和后续分析都失真。
- 只有先保留全量，后续才可能在不同消费场景下做不同裁剪策略。

备选方案：
- 仅把 20 提到更大的固定值，例如 50。放弃原因：仍然是人为截断，不满足“尽可能齐全”目标。

### D4: 涨停股兜底结果必须显式区分“正式涨停池”与“近似候选集”

选择：
- 当使用专用涨停池主源时，返回正式涨停池语义。
- 当退化到快照按涨跌幅过滤时，保留结果，但增加来源/质量标记，表明它是近似集合而不是严格涨停池。

理由：
- “尽量获取齐全”不等于“模糊不同口径”。
- 兜底快照有价值，但其制度口径无法完全等价于正式涨停池。

备选方案：
- 兜底时直接返回空列表。放弃原因：会丢失可用的候选信息，不符合完整性优先目标。

### D5: 板块 contract 升级为 `top 10 + bottom 10`

选择：
- 保持当前“上下榜分离”的摘要结构不变。
- 将单侧数量从 5 提升到 10，总量提升到 20。

理由：
- 这能最小化对下游格式的破坏，同时明显提升 AI 输入的广度。
- 继续保留“上涨最强 / 下跌最弱”结构，比返回单一混排列表更适合总结。

备选方案：
- 返回全量板块列表。放弃原因：对当前 `market-summary` 目标来说噪音过高，且会显著放大 prompt 体积。

### D6: CLI 与 AI 输入摘要同步暴露更丰富的质量和规模信息

选择：
- CLI 阶段 1 需要能区分 `near-complete` 与 `partial`。
- AI 输入摘要需要能感知板块已扩展到 20 个、涨停股为全量池或近似集合，并在必要时做展示裁剪。

理由：
- 如果底层 contract 升级但上层仍按旧文案输出，用户会继续误判为“不完整”或“只有 20 条”。
- AI prompt 如果不做适度裁剪，涨停股全量可能推高 token 成本，因此裁剪应上移到 prompt 层而不是数据层。

## Risks / Trade-offs

- [`pytdx` 补抓仍可能无法补齐] → 保留 `near-complete / partial / error` 分层，并把缺失规模显式暴露给 CLI。
- [涨停股全量会放大缓存与 prompt 体积] → 数据层保留全量，CLI/AI 消费层按场景裁剪，避免把展示约束写死在抓取层。
- [新增质量状态会扩大测试面] → 通过 contract 测试覆盖 `ok / near-complete / partial / error` 四类路径，避免只测 happy path。
- [板块数量增加可能让摘要更长] → 保留上下榜结构，必要时在 prompt 构造时采用分组或截断策略。

## Migration Plan

1. 调整 `FinanceClient` contract，先完成涨跌统计质量分层、涨停股全量语义和板块数量扩展。
2. 调整缓存门控，使 `market_statistics` 支持 `near-complete` 写入，并确认旧缓存不会被坏数据覆盖。
3. 调整 `market-summary` CLI 与 AI 输入摘要，使新 contract 对用户可见且可解释。
4. 更新回归测试与 contract 测试，覆盖新状态、全量涨停池和 20 个板块输入。

## Open Questions

- `near-complete` 的判定阈值应按“绝对缺失数”还是“缺失比例”定义，还是两者结合。
- AI 输入层面对全量涨停股的裁剪应按条数、连板数优先级，还是按来源质量分层。
- 是否需要把涨停股“正式池 / 近似候选集”的来源标记持久化到缓存，还是仅保留在运行时 payload 中。
