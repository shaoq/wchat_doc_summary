## Context

当前 `market-summary` 命令在进入 AI 生成前，已经输出了阶段 1、阶段 2 的逐项状态，并在阶段 2 与阶段 3 之间补充了一个 `[预检] 当前抓取结果` 汇总块。但这个汇总块仍然是按“成功 / 失败 / 无数据”分组聚合的，用户需要再自行反向推断每一类输入数据当前处于什么状态。

这次变更的目标不是改造市场数据或新闻数据的采集逻辑，也不是扩展 AI 输入 contract，而是把 CLI 在 AI 开始前的可见性收口成一份稳定、直接、逐项的输入数据清单。

## Goals / Non-Goals

**Goals:**
- 在 AI 开始总结前，稳定输出逐项输入数据清单。
- 对每类输入数据统一展示三类信息：类型、状态、数量或计数摘要。
- 复用现有市场数据和新闻数据状态归一化逻辑，避免引入新的底层 contract。
- 让用户能够快速判断“AI 将基于哪些输入生成总结”。

**Non-Goals:**
- 不扩展 `MarketAnalyzer.collect_market_data()` 的返回结构。
- 不展示更细的 adapter、来源或降级路径。
- 不调整市场数据采集、新闻聚合或 AI prompt 组织逻辑。
- 不改变阶段 1 与阶段 2 的现有摘要输出语义。

## Decisions

### 1. 在阶段 2 和阶段 3 之间展示固定的“输入数据清单”

选择：保留当前阶段 1 与阶段 2 的输出，在进入 AI 生成前新增一段逐项清单，作为最终预检视图。

理由：
- 用户真正关心的是“AI 开始前最终掌握了哪些输入”，而不是单独查看每个阶段的分散日志。
- 将清单放在阶段 3 之前，语义最直接，也不会打乱已有阶段结构。

备选方案：
- 只增强阶段 1、阶段 2 的现有输出，不新增统一清单。放弃原因：用户仍需自己跨阶段拼接结果。

### 2. 复用现有状态项构造函数，不新增底层数据字段

选择：继续基于 `_get_market_data_status_items()` 与 `_get_news_status_items()` 生成统一的状态项，再按固定顺序渲染为逐项清单。

理由：
- 这些函数已经把不同来源数据归一化成 `label / status / message / summary` 结构，足以支撑本次展示需求。
- 不改 `MarketAnalyzer` contract，能把变更范围控制在 CLI 编排层和测试层。

备选方案：
- 让 `MarketAnalyzer` 直接返回完整 manifest。放弃原因：需求只需要 CLI 展示，扩展底层 contract 会放大改动面。

### 3. 使用固定顺序逐项展示，而不是按状态分组

选择：按稳定的输入类型顺序展示：
指数、成交额、涨跌统计、板块、涨停股、财联社电报、看盘数据、相关文章。

理由：
- 用户关注的是“某一类输入有没有拿到”，逐项顺序展示更容易扫描和对比。
- 固定顺序比“成功 / 失败 / 无数据”分组更稳定，也更便于测试。

备选方案：
- 保留分组汇总，只补充更多文案。放弃原因：仍然不满足“直接查看每类输入状态”的目标。

## Risks / Trade-offs

- [阶段 1/2 已有逐项状态，阶段 3 前再展示一次可能显得重复] → 新清单明确定位为“AI 输入清单”，强调它是生成前的最终视图，而不是重复日志。
- [数量摘要格式不完全一致] → 继续复用现有 `summary` 文案，保证市场数据与新闻数据的计数口径一致。
- [后续若新增新的输入类型，清单渲染需要同步更新] → 用统一状态项列表和固定顺序集中管理，降低未来扩展成本。
