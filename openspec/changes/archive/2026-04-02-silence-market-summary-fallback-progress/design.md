## Context

当前 `market-summary` 的主 CLI 编排实际上已经是串行阶段模型：

1. 获取市场数据
2. 获取新闻数据
3. 生成并保存市场总结

分析代码后可以确认，AI 阶段只会在阶段 1 和阶段 2 的 `await` 都返回后才开始；问题不在“AI 提前启动”，而在于降级路径的终端表现会让这一点变得不清楚。

当东方财富主快照不完整时，成交额和涨跌统计会分别回退到 `akshare.stock_zh_a_spot_em()`。这两个备用调用当前是彼此独立且并发触发的，因此会在同一轮 `market-summary` 执行中同时出现多条 `akshare` 内部分页 `tqdm`。这些原始进度条与 `rich` 的阶段状态混在一起，终端会出现进度覆盖、控制字符残留和“看起来像还没收尾就进入下一阶段”的错觉。

这次设计的目标不是重做 `market-summary` 的整体编排，也不是改 AI prompt，而是把“阶段边界真实语义”和“降级路径的输出噪音”一起收口，保证 CLI 在正常和退化场景下都可读、可解释。

## Goals / Non-Goals

**Goals:**
- 保持 `market-summary` 的现有三阶段编排结构不变，但让阶段边界语义在用户视角下更清晰。
- 确保 AI 生成只发生在市场数据和新闻数据都形成最终输入后。
- 让成交额和涨跌统计在降级到 `akshare.stock_zh_a_spot_em()` 时共享同一次全市场抓取结果。
- 屏蔽或吸收第三方原始进度条，避免其直接污染 CLI 阶段输出。
- 为上述行为补充回归测试，锁定阶段顺序、备用源复用和静默输出要求。

**Non-Goals:**
- 不调整 `market-summary` 的 AI 模板、prompt 结构或总结章节。
- 不在本次变更中把新闻聚合从串行改为并行。
- 不扩展市场数据种类，也不重写现有 source strategy 的整体层级。
- 不修改第三方 `akshare` 包源码。

## Decisions

### 1. 保持现有阶段编排，只收紧阶段完成定义

选择：不改 `market-summary` 的三阶段结构，而是把“阶段完成”定义为“本阶段内部所有抓取与降级尝试都已经结束，并产出最终输入状态”。

理由：
- 当前 CLI 主链路已经满足“阶段 1、阶段 2 完成后才进入阶段 3”，没有必要为这次问题重构编排层。
- 用户感知到的混乱主要来自第三方进度输出污染，而不是业务流程真的乱序。
- 保持主流程结构不变，可以把改动集中在终端输出治理和备用源复用上。

备选方案：
- 改造成更细粒度的子阶段或显式任务图。放弃原因：复杂度高，且无法直接解决 `akshare` 输出干扰。

### 2. 为宽度数据新增“共享备用快照”路径

选择：当主快照不可用时，不再让成交额和涨跌统计分别调用 `_get_volume_data_from_spot_em()` / `_get_statistics_from_spot_em()`，而是先获取一次 `akshare.stock_zh_a_spot_em()` 的 DataFrame，再从这一份结果同时计算两个输出。

理由：
- 当前最明显的冗余就是同一轮降级中重复抓取全市场 A 股快照，两次抓取既耗时，又会触发两条分页进度。
- 成交额和涨跌统计天然是同一市场截面的两个衍生视图，共享备用快照与主路径“共享东方财富快照”的思路一致。
- 复用同一次备用抓取后，两个结果也能保持更一致的时间点语义。

备选方案：
- 仅关闭进度条，但保留两次独立抓取。放弃原因：能减轻刷屏，但无法消除额外耗时和重复网络请求。
- 完全禁用 `akshare` 备用源。放弃原因：会削弱当前宽度数据降级能力。

### 3. 在项目侧静默 `akshare` 原始分页进度，而不是依赖终端兼容性

选择：在本项目调用 `akshare` 的关键路径中，主动关闭或隔离其内部 `tqdm` 输出，让 CLI 只显示自己管理的 `rich` 阶段信息。

理由：
- 这些原始进度条是第三方库内部实现细节，不属于 `market-summary` 对用户承诺的输出 contract。
- 当前 `rich` 和 `tqdm` 混用时会出现覆盖和控制字符残留，问题不是文案层能解决的。
- 在项目侧治理输出，比要求用户终端兼容或接受噪音更可控。

备选方案：
- 接受原始 `tqdm`，仅在文档里说明。放弃原因：不能满足 CLI 稳定可读的目标。
- 直接重定向整个阶段的标准输出/错误输出。放弃原因：范围过大，容易误伤本项目自己的提示与异常输出。

### 4. 用测试锁定“干净阶段输出”而不是只锁定结果数据

选择：除了现有结果正确性测试外，还要增加 CLI/finance 层回归测试，验证：
- AI 阶段只出现在阶段 1、阶段 2 之后
- 备用宽度数据只触发一次全市场 `akshare` 抓取
- CLI 输出中不再出现原始 `tqdm` 进度特征或控制字符

理由：
- 这次问题的核心是执行体验与阶段可解释性，单看最终 `market_data` 结构无法覆盖。
- 没有输出层测试，后续很容易因 source strategy 调整再次把第三方进度条带回来。

备选方案：
- 只测返回值，不测输出。放弃原因：无法保护这次变更的主要目标。

## Risks / Trade-offs

- [静默第三方进度条可能掩盖长耗时调用] → CLI 继续保留阶段状态和最终结论，必要时可在日志层记录耗时，而不是把第三方内部进度直接暴露给用户。
- [共享备用快照会让一次失败同时影响成交额和涨跌统计] → 这是与主路径一致的设计取向；若共享抓取失败，仍可统一标记该轮备用链路失败，语义更清晰。
- [输出治理实现方式如果过宽，可能吞掉有价值错误信息] → 设计上优先选择仅关闭 `akshare` 进度构造器或局部包裹其调用，不做全局 stdout/stderr 粗暴重定向。
- [现有进行中的 `complete-market-summary-snapshot-pagination` 也修改 `src/api/finance.py`] → 实施阶段需要以“共享备用快照”和“静默输出”为独立责任边界，避免与分页主链路修复产生无谓冲突。

## Migration Plan

1. 在 `FinanceClient` 中梳理宽度数据降级路径，引入一次抓取、多处计算的共享备用快照能力。
2. 在项目调用 `akshare` 的相关路径上增加静默进度的治理层，避免原始 `tqdm` 进入 CLI。
3. 保持 `market-summary` 现有阶段结构，仅在必要处补强阶段结论与生成前语义验证。
4. 更新 CLI 与 finance 相关测试，覆盖阶段顺序、备用源复用和无原始进度条输出。
5. 在真实 `market-summary --force` 路径上回归验证降级场景。

回滚策略：
- 若静默输出方案影响异常排查，可先保留共享备用快照优化，仅回退静默策略实现，同时确保不恢复重复全量抓取。

## Open Questions

- 静默 `akshare` 进度条的最佳实现点是否应集中在本项目的统一 helper，而不是分散在各个 adapter 调用点。
- 是否需要在 CLI 上额外提示“当前走了静默降级路径”，还是仅保留现有状态与日志即可。
