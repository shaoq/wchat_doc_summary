## Context

当前 `FinanceClient` 已经承担了市场总结所需的大部分实时市场数据聚合职责，输出 contract 也已基本稳定，因此这次变更不再讨论“历史交易日重建”或“更换整套数据源”。问题集中在实时链路内部的三个层面：

- 同一轮总结中，成交额和涨跌统计都会各自重复扫描全市场股票列表，导致网络请求和等待时间被放大。
- 板块数据当前来源于同花顺 HTML 页面，解析结果没有稳定 `sector_code`，但缓存层又要求板块行具备稳定唯一键，导致板块缓存存在天然冲突风险。
- `MarketAnalyzer` 已支持“最近一个交易日”的默认选择，但部分实时数据项仍固定绑定 `date.today()` 或当前接口语义，导致“最近一个交易日”场景下数据项之间可能不完全一致。

这些问题不会让命令完全不可用，但会持续侵蚀实时总结的稳定性、缓存有效性和执行性能。

## Goals / Non-Goals

**Goals:**
- 让实时市场数据在“今天 / 最近一个交易日”场景下使用一致的目标日期语义。
- 让成交额和涨跌统计共享同一份全市场快照，减少重复抓取。
- 让板块数据能够稳定写入并读出缓存，而不是依赖脆弱的空标识行为。
- 明确实时链路实际生效的重试、降级和短时复用策略。
- 用回归测试锁住以上行为。

**Non-Goals:**
- 不实现任意历史交易日的完整市场数据重建。
- 不在本次变更中更换新浪、腾讯、同花顺、akshare 或 CLS 这些现有数据源。
- 不重构 `market-summary` 的整体编排方式，只修正其对实时市场数据的调用语义。
- 不扩展新的市场数据维度。

## Decisions

### 1. 为实时链路引入“单次股票快照”复用，而不是分别计算成交额和涨跌统计

当前成交额和涨跌统计都依赖新浪全市场股票列表，但它们分别独立调用 `get_all_stocks()`。本次改造将把“抓取全市场实时股票快照”提升为显式的可复用步骤：

- 一次抓取全市场股票列表
- 成交额基于同一快照计算
- 涨跌统计基于同一快照计算

这样可以降低实时链路的网络成本和等待时间，也使“同一轮总结中的成交额和涨跌统计来自同一时刻快照”成为显式语义。

备选方案：
- 继续分别抓取两次，依赖底层 TTL 缓存。放弃原因：当前缓存并未真正接入主流程，且即便接入，语义上也不如一次快照清晰。

### 2. 板块缓存使用稳定键，而不是继续依赖空 `sector_code`

现有同花顺板块源无法直接提供板块代码，但缓存表对 `(trade_date, sector_code)` 做唯一约束。本次实现需要在“数据源无代码”的前提下生成稳定标识：

- 优先从页面链接或结构中提取稳定标识
- 若当前源确实没有稳定代码，则在实时链路内使用可重复生成的派生键
- 缓存层和读取层统一使用这一稳定键

目标不是让板块键变成行业标准代码，而是先让缓存稳定可用。

备选方案：
- 完全禁用板块缓存。放弃原因：会让收盘后缓存缺口持续存在，也回避不了板块数据在市场总结中的价值。

### 3. 实时市场数据 API 以“目标交易日是今天或最近一个交易日”为约束

不做历史重建后，实时链路的合理边界应明确为：

- 当目标交易日等于今天：直接使用当前实时源
- 当目标交易日是最近一个已结束交易日：允许使用明确支持目标日期的数据项，或使用该日期缓存
- 不允许某些数据项偷偷固定到系统当天，而另一些数据项基于最近交易日

尤其涨停股等当前固定使用 `date.today()` 的数据项，需要改为接收目标日期参数，并在“最近一个交易日”场景下与整体 trade_date 对齐。

备选方案：
- 保留少量数据项使用系统当天，并认为偏差可接受。放弃原因：会让同一份总结里的数据项时态不一致，排查困难。

### 4. 重试和短时复用要么真正接入，要么移除伪能力

当前 `FinanceClient` 内存在 `_retry_request` 和模块级缓存变量，但主链路并未真正使用。本次变更选择“接入真实能力”而不是继续保留死代码：

- 统一把适合的同步抓取调用接到共享重试/超时封装上
- 对适合短时复用的实时快照使用显式 TTL 缓存
- 不适合缓存的调用仍保持直取，但不再保留误导性占位逻辑

备选方案：
- 删除所有未接入能力。放弃原因：实时取数本身确实需要重试和短时复用，只是当前实现半成品。

## Risks / Trade-offs

- [共享股票快照会引入更大的单次内存对象] → 快照只在单次聚合内短暂存在，并用 TTL 控制可复用窗口。
- [派生板块键可能在源页面命名变化时漂移] → 派生规则要尽量基于结构化字段，并通过测试锁定当前行为。
- [最近一个交易日语义会暴露个别数据源对日期参数支持不足] → 对不支持的源明确降级，而不是默默使用系统当天。
- [统一接入重试可能拉长失败时延] → 仅对外部抓取调用设置有限重试次数与合理超时。

## Migration Plan

1. 先梳理实时取数入口，抽出全市场股票快照复用点。
2. 修正板块标识和缓存写入逻辑，确保缓存能稳定落库。
3. 调整涨停股等日期敏感数据项，使其接受目标交易日参数。
4. 将共享重试/短时缓存接入真实主链路。
5. 最后补齐实时链路回归测试并验证市场总结主流程。

回滚策略：
- 若共享股票快照改造引入问题，可暂时回退为独立计算，但保留其它语义修正。
- 若板块稳定键方案不可靠，可先停用板块缓存写入，而不是继续使用空键落库。

## Open Questions

- 板块稳定键是否优先使用页面链接中的隐藏标识，还是以板块名称标准化结果作为当前阶段唯一键；需要实现时看页面实际结构确定。
- 短时缓存应放在 `FinanceClient` 级别还是更靠近数据源 adapter；两者都可行，但需要避免与数据库缓存语义混淆。
