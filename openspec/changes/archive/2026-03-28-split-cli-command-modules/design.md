## Context

当前 CLI 文件 [src/cli.py](/Users/jie.hua/Documents/Developments/Projects/wchat_doc/src/cli.py) 同时承担：

- 顶层命令与子命令定义
- `market-summary`、抓取、导出、AI 处理等业务流程编排
- `Rich` 表格和面板展示
- 一些辅助格式化函数

文件已经超过 1300 行，且多个未来 change 都会触碰 CLI。继续保持单文件结构会带来两个直接问题：

- 不同功能线改动极易在同一文件上冲突
- 任何命令级改动都需要在庞大文件中定位，维护成本持续上升

本次变更只做 CLI 结构治理，不改变命令面语义。

## Goals / Non-Goals

**Goals:**
- 将 CLI 按业务领域拆分为多个命令模块
- 保持统一入口与现有命令名、子命令名不变
- 降低多条 change 并行实施时在 CLI 层的冲突概率
- 为后续继续增加命令组或拆分服务层创造更稳定的边界

**Non-Goals:**
- 不修改命令行为语义
- 不在本次变更中同步重构所有业务逻辑到服务层
- 不引入新的 CLI 框架，继续使用 Click

## Decisions

### 1. 保留单一入口模块，增加领域命令模块

CLI 将保留统一入口，但命令定义按领域拆分，例如：

- subscription / fetch
- article / export
- ai / stocks
- market

入口模块只负责创建根 `Click` group 并注册子模块命令。

备选方案：
- 完全替换为包级入口并重写启动方式。放弃原因：改动面过大，且本次不需要改变对外调用方式。

### 2. 先拆命令声明与注册，再逐步下沉业务逻辑

本次优先解决文件组织问题，而不是同步完成 CLI 与业务逻辑的全面分层。命令函数可以先迁移到领域模块中，再在后续 change 中继续下沉复杂流程。

备选方案：
- CLI 拆分与业务分层同时完成。放弃原因：范围过大，容易把结构治理变成混合重构。

### 3. 帮助信息与命令面视为回归保护对象

模块化拆分后必须保持：

- 顶层命令名不变
- 子命令名不变
- `--help` 输出中的命令面可用

这保证变更是结构性的，而不是用户可见的功能变更。

备选方案：
- 借拆分机会一起重命名命令组。放弃原因：会增加迁移成本，也不符合本次目标。

## Risks / Trade-offs

- [拆分过程中改变命令注册顺序或遗漏子命令] → 用 CLI help 回归测试覆盖顶层和 `ai` 子命令命令面
- [不同模块相互 import 导致循环依赖] → 入口模块只做注册，命令模块只依赖服务层和共享展示工具
- [结构拆分后业务逻辑仍然分散] → 接受为阶段性结果，本次先解决文件冲突和组织问题

## Migration Plan

1. 识别当前 CLI 的命令边界和共享辅助函数
2. 新建领域命令模块并迁移命令声明
3. 在入口模块中完成统一注册
4. 增加 help 与关键命令面回归测试
5. 验证命令行为未发生用户可见变化

回滚策略：
- 若模块化注册出现遗漏，可临时回退到单文件 CLI，同时保留已识别出的模块边界与测试
