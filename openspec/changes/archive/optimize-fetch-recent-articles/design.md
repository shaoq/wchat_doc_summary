## Context

当前 `FetcherService.fetch_feed()` 方法会遍历公众号的所有历史文章（默认最多 5 页），每篇文章都会检查是否已存在于数据库中。这种方式的问题：

- API 请求配额有限，大量请求浪费在已抓取的历史文章上
- 每次抓取都需要进行大量数据库查询检查文章是否存在
- 用户通常只关心最近发布的新文章

## Goals / Non-Goals

**Goals:**
- 默认只抓取最近 5 天的文章，减少不必要的 API 请求
- 提供参数让用户可以自定义抓取时间范围
- 保留全量抓取能力，通过 `--full` 参数触发

**Non-Goals:**
- 不改变现有的分页逻辑
- 不改变文章存储格式
- 不影响增量抓取 (`fetch_incremental`) 方法

## Decisions

### 1. 时间过滤实现位置

**决定**: 在 `fetch_feed()` 方法内部实现时间过滤

**原因**:
- API 不支持时间范围参数，只能通过客户端过滤
- 在获取每页数据后立即过滤，可以更早终止遍历

**替代方案**:
- 在 CLI 层过滤：需要在获取所有数据后再过滤，无法提前终止
- 修改 API 调用：API 不支持此功能

### 2. 默认天数选择

**决定**: 默认 5 天

**原因**:
- 大多数公众号每周发布 1-3 篇文章
- 5 天可以覆盖一周的发布周期
- 定时任务（如每天运行）不会遗漏文章

### 3. CLI 参数设计

**决定**: 使用 `--days N` 和 `--full` 参数

```bash
wchat fetch --all              # 抓取所有订阅，最近 5 天
wchat fetch --all --days 10    # 抓取所有订阅，最近 10 天
wchat fetch --all --full       # 抓取所有订阅，全部历史
wchat fetch MP_WXS_xxx         # 抓取指定公众号，最近 5 天
wchat fetch MP_WXS_xxx --full  # 抓取指定公众号，全部历史
```

**原因**:
- `--days` 灵活可配置
- `--full` 保留原有行为，向后兼容

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 用户不知道默认行为已变更 | 在帮助信息和执行时显示抓取范围提示 |
| 5 天内无新文章时返回空列表 | 提示用户可使用 `--full` 获取更多 |
| 时区问题导致漏抓 | 使用本地时间计算，与发布时间比较时考虑时区 |
