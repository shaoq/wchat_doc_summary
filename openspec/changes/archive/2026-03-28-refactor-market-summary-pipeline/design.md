## Context

当前 `market-summary` 由 CLI 直接编排 `MarketAnalyzer`、`FinanceClient` 和 `AIProcessor`，已经能生成最小版本的交易日总结，但有几类系统性问题：

- 主流程直接调用 `FinanceClient`，未复用已有的 `MarketDataCacheService`
- 实时数据、缓存数据、CLI 展示和 prompt 组装之间的字段结构不一致
- 财联社重要电报已被抓取，但未进入 AI prompt；财联社看盘数据已有模块但未进入总结流程
- `--offline` 当前返回空行情结构，与“离线生成总结”的用户认知不一致
- 相关文章仍按“最近 N 天”粗略筛选，缺少交易日语义
- CLI 中混杂了流程编排、格式化、异常兜底和存储逻辑，导致行为修复容易波及多处

这次改造横跨 CLI、服务层、缓存层、模板和测试，是一次明确的跨模块流程治理，而不是单点修复。

## Goals / Non-Goals

**Goals:**
- 让 `market-summary` 在线、缓存、离线三条路径共用同一套市场数据结构
- 将市场数据缓存正式接入总结主流程，建立可解释的命中与刷新策略
- 将财联社重要电报与财联社看盘数据正式接入总结输入
- 将相关文章筛选改为面向交易日的时间窗口
- 收敛 CLI 负责范围，降低流程行为散落在多个模块中的问题
- 为关键分支补上流程级测试，确保后续迭代不再回归

**Non-Goals:**
- 不重写 `FinanceClient` 的底层数据源实现
- 不在本次变更中扩展新的市场数据来源
- 不重构整个文章抓取链路，只调整 `market-summary` 对文章的筛选方式
- 不修改数据库表结构，除非实现阶段发现当前字段无法表达统一返回结构

## Decisions

### 1. 由 `MarketAnalyzer` 负责“总结输入包”编排，CLI 只负责参数和展示

`src/cli.py` 仍保留命令入口与终端输出，但不再承担过多的市场总结流程决策。`MarketAnalyzer` 负责：

- 交易日选择
- 市场数据获取策略选择（实时 / 缓存 / 离线）
- 新闻聚合
- 相关文章筛选
- 最终交给 `AIProcessor` 的输入包组装

这样可以把 `market-summary` 的业务语义集中到服务层，避免 CLI 继续膨胀。

备选方案：
- 继续在 CLI 中追加流程判断。放弃原因：现有 CLI 已过重，后续很难测试与复用。

### 2. 定义统一的市场总结输入结构，缓存路径与在线路径完全对齐

本次改造将引入统一的 `market_data` 结构约束，要求：

- 实时获取返回什么，缓存读取就返回什么
- CLI 摘要展示与 prompt 组装都只消费这一套结构
- 指数字段统一使用 `close`，不再混用 `price`

缓存服务需要适配为同结构输出，否则接入缓存只会引入更多分支。

备选方案：
- 在 CLI 和 `AIProcessor` 层兼容两套结构。放弃原因：复杂度高，且会继续放大字段漂移。

### 3. 缓存策略按“交易日状态 + force 参数”决定，而不是按调用方分叉

缓存行为统一由 `MarketAnalyzer` 驱动：

- 历史交易日：优先读缓存，缓存缺失则抓取并回填缓存
- 当天未收盘：默认实时抓取，不写静态缓存
- 当天已收盘：允许抓取并写缓存
- `--force`：跳过缓存直接抓取；如满足缓存条件则覆盖缓存
- `--offline`：只读取本地缓存与本地新闻/文章，不触发任何网络请求

备选方案：
- 让 CLI 直接决定缓存逻辑。放弃原因：缓存策略属于业务规则，不应散落在入口层。

### 4. 财联社数据采用“聚合后再入 prompt”的模式，而不是把原始源数据直接塞进模板

总结流程中的新闻输入将分成三类：

- `cls_telegraphs`
- `cls_watch_items`
- `related_articles`

`MarketAnalyzer` 负责收集和裁剪，`AIProcessor` 只负责格式化后注入模板。这样能避免模板直接依赖抓取层返回结构，也便于后续扩展新的新闻来源。

备选方案：
- 让 `FinanceClient` 直接返回适配 prompt 的文本。放弃原因：会把抓取层和 AI 表达层耦合在一起。

### 5. 文章筛选窗口改为交易日相关时间窗，而不是固定回溯天数

`get_related_articles()` 将不再使用简单的 `days_back=3`。新的筛选逻辑基于交易日窗口，保证：

- 纳入与该交易日最相关的盘前、盘中、盘后分析
- 减少节假日或长周末带来的噪声文章
- 在 CLI 输出中可解释和可调试

备选方案：
- 保留按天数回溯，只调参数。放弃原因：无法从根本上解决交易日错配问题。

## Risks / Trade-offs

- [缓存结构与实时结构不一致] → 在实现前先统一 schema，并为缓存路径补上单测
- [离线模式无缓存可用时体验变差] → 明确输出“无可用本地市场数据”，而不是静默生成空行情总结
- [财联社看盘数据质量不稳定] → 聚合层允许缺省单个来源，不因单一来源缺失阻断总结生成
- [流程下沉到服务层后改动面较大] → 先补流程测试，再做编排收敛，降低回归风险
- [交易日文章窗口规则仍可能有边界争议] → 在 CLI 中打印实际窗口，并保留后续迭代空间

## Migration Plan

1. 先修复 `--list` 和电报未传入 prompt 的显式错误
2. 引入统一 `market_data` 结构并让缓存服务对齐
3. 将 `MarketAnalyzer.collect_market_data()` 切换为缓存优先策略
4. 接入财联社看盘数据与新闻聚合逻辑
5. 切换相关文章筛选到交易日时间窗
6. 最后补齐 CLI 与流程级测试，并用现有数据库样本验证输出

回滚策略：
- 若新聚合流程出现问题，可临时回退到“实时行情 + 本地文章”的最小闭环
- 缓存逻辑接入失败时，可保留统一 schema 改造成果，单独回退缓存读写策略

## Open Questions

- 财联社看盘数据应由 `FinanceClient` 拉取，还是由 `MarketAnalyzer` 通过独立服务读取本地存储；实现阶段需要结合现有存储路径做最终确认
- 交易日相关文章的精确窗口边界是否统一为“上一交易日收盘后至当日收盘后”，还是保留盘前缓冲区；需要结合现有文章发布时间分布做一次校验
