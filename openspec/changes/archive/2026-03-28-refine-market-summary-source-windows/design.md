## Context

`market-summary` 现在已经有三类资料来源：

- 财联社看盘数据
- 财联社重要电报
- 市场相关文章

但这三类资料并不应该使用同一套时间窗口。看盘更像交易日盘中的“走势过程”，电报更像“盘中到下个交易日前的消息流”，文章则更偏“盘后复盘和开盘前观点”。如果仍然把它们混在同一套窗口定义里，系统虽然能运行，但资料职责会变得模糊，尤其在周末、节前和周一开盘前场景下会放大歧义。

另一个基础问题是默认 `trade_date` 的确定。非交易日执行时，系统应该先回退到最近交易日，再围绕该交易日计算各资料类型的窗口，而不是直接用当前自然日往下推导。

## Goals / Non-Goals

**Goals:**
- 明确默认 `trade_date` 在非交易日和开盘前场景下的回退规则。
- 为看盘、电报、文章定义各自稳定且可解释的时间窗口。
- 让实际查询窗口与 CLI 展示窗口保持一致。
- 让市场总结输入更贴合三类资料的真实职责。

**Non-Goals:**
- 不调整市场数据本身的实时抓取逻辑。
- 不引入新的资料来源。
- 不在本次变更中改变 AI 模板结构，只调整输入时间窗口语义。

## Decisions

### 1. 默认 `trade_date` 先回退到最近交易日

非交易日执行时，默认 `trade_date` 必须先回退到最近交易日；如果是交易日但尚未开盘，则回退到上一个交易日。

选择理由：
- 市场总结的语义是“总结某个交易日”
- 周末执行时如果直接把自然日当成 `trade_date`，后续所有资料窗口都会偏移

备选方案：
- 继续使用当前自然日，并在后续窗口中补救。放弃原因：会让三类资料窗口都变得反直觉。

### 2. 看盘数据只覆盖交易日盘中

看盘窗口定义为：

- `trade_date 09:00 ~ trade_date 15:00`

选择理由：
- 看盘数据本质上描述盘中走势、轮动和异动
- 如果把盘后甚至周末内容也纳入看盘，会稀释它的职责

备选方案：
- 使用 `trade_date 09:00 ~ next_trade_date 09:00`。放弃原因：会把盘后和周末信息混入看盘语义。

### 3. 财联社电报覆盖盘中到下一个交易日前

电报窗口定义为：

- `trade_date 09:00 ~ next_trade_date 09:15`

选择理由：
- 你明确要求把交易日盘中重要电报纳入
- 电报同时需要承接盘后、周末和下个交易日开盘前的消息流

备选方案：
- `trade_date 15:00 ~ next_trade_date 09:15`。放弃原因：会丢掉交易日盘中重要消息。
- `trade_date 00:00 ~ next_trade_date 09:15`。放弃原因：会引入较多凌晨噪声，且与“盘中消息”诉求相比收益不高。

### 4. 文章仍聚焦盘后到下一个交易日前

文章窗口保持为：

- `trade_date 15:00 ~ next_trade_date 09:15`

选择理由：
- 文章更适合作为收盘后复盘和开盘前观点来源
- 不把盘中文章混进来，可以减少噪声

备选方案：
- 将文章窗口也扩展到 `09:00`。放弃原因：容易引入盘中即时资讯，和看盘、电报职责重叠。

### 5. CLI 要按资料类型展示窗口，而不是假装只有一个总窗口

既然三类资料窗口不同，CLI 就不应只展示一个模糊的总窗口。展示层应该和查询层保持一致，必要时分别展示：

- 看盘窗口
- 电报窗口
- 文章窗口

备选方案：
- 继续只显示文章窗口。放弃原因：会误导用户以为所有资料都按同一窗口获取。

## Risks / Trade-offs

- [电报和看盘在盘中会有部分重叠] → 通过职责区分化解：看盘描述走势，电报描述消息。
- [CLI 展示信息会变多] → 用简洁格式分别展示三类窗口，避免信息堆叠。
- [周末和节前窗口测试更复杂] → 补明确的时间窗口用例，尤其覆盖周五到周一场景。

## Migration Plan

1. 先修正默认 `trade_date` 的回退逻辑。
2. 为三类资料分别定义并实现窗口计算。
3. 让查询层和 CLI 展示层共用同一套窗口对象。
4. 最后补齐周末、开盘前和节前场景测试。

回滚策略：
- 若分资料窗口展示影响过大，可先保留查询语义修正，仅简化展示文案，但不能回滚默认 `trade_date` 回退逻辑。

## Open Questions

- CLI 是否需要始终展示三类窗口，还是只在 `--verbose` 模式下展开显示。
- 财联社电报窗口的结束时间是否长期固定为 `09:15`，还是应和实际盘前准备时间一起配置化。
