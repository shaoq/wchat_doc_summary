## Context

当前 `FinanceClient` 已经把指数、成交额、涨跌统计、板块和涨停股收敛成统一 contract，但“每类数据究竟来自哪个源、何时降级、失败后如何兜底”仍然主要隐含在实现里。现实上，这几类数据的稳定性并不对称：
- 指数路径相对稳定，已有腾讯与 akshare 两层退路
- 成交额与涨跌统计依赖全市场实时快照，当前共享快照后成本更低，但主路径仍偏向东方财富实时接口
- 板块与涨停股对东方财富实时 `curl` 的依赖更脆弱，历史设计里也已经识别过板块和涨停池应优先走更稳定的专用接口

如果继续以“单个方法内塞若干 if/else fallback”演进，后续很容易再次出现注释、设计和真实行为漂移。需要把 source strategy 本身变成一等设计对象。

## Goals / Non-Goals

**Goals:**
- 为每类市场数据定义显式主源、备源和失败兜底语义
- 保持 `FinanceClient` 对外 contract 不变，让上层仍消费统一结构
- 优先提升板块和涨停股的稳定性，减少对已知脆弱实时路径的主依赖
- 让 source selection 和 fallback 行为可测试，而不是只靠运行日志判断

**Non-Goals:**
- 不在本次 change 中引入付费第三方数据服务
- 不重写 `market-summary` 的编排层
- 不要求所有数据项都切到同一个源

## Decisions

### 1. 按数据类型定义 source adapter，而不是按 `FinanceClient` 整体定义单一主源

选择：把指数、全市场快照、板块、涨停股视为不同数据类别，各自拥有独立 source strategy。

理由：
- 这些数据天然来自不同接口，稳定性和成本也不同。
- “一个全局主源 + 一个全局备源”无法准确表达真实链路。

备选方案：
- 继续维持当前方法内局部 fallback。缺点是规则分散，不利于测试和后续替换。

### 2. 指数保留腾讯为主，成交额/涨跌统计保留单次快照复用

选择：
- 指数：腾讯实时接口主，akshare 指数接口备
- 成交额/涨跌统计：继续基于单次全市场快照计算，保留当前“抓一次算两项”的模式

理由：
- 指数当前链路已经是几类数据里最稳定的一类
- 成交额与涨跌统计共享快照能减少等待时间，并保持两者时间一致性

备选方案：
- 全量切到 akshare DataFrame 口径。优点是实现更统一，缺点是实时成本更高，且未必提升真实独立性。

### 3. 板块与涨停股优先切到更稳定的专用源，实时 `curl` 退居备份

选择：
- 板块：优先使用更稳定的专用板块接口适配器，实时东方财富 `curl` 不再作为默认主路径
- 涨停股：优先使用专用涨停池接口适配器，实时全市场快照筛选只作为退路或实时补位

理由：
- 这两类是当前最脆弱的部分，也是用户在市场总结里最依赖的结构化信号
- 专用接口在语义上也比“从全市场快照里二次筛选”更接近业务目标

备选方案：
- 继续保持东方财富实时 `curl` 为主。放弃原因：已知在部分时段和环境下不稳定。

### 4. source strategy 必须显式映射到 contract 的空值语义

选择：无论哪个 adapter 命中，`FinanceClient` 仍只输出统一 contract；当某类源全部失败时，返回既定零值/空结构，而不是抛出源特有错误。

理由：
- 上层消费方已经依赖当前统一 contract
- 稳定 source strategy 的目标不是把源差异暴露给上层，而是把不稳定性隔离在聚合层

## Risks / Trade-offs

- [更稳定的专用板块/涨停股接口也可能变动] → 通过 adapter 隔离具体实现，保留明确备份路径
- [不同数据项继续多源并存，维护成本不会为零] → 用显式策略表和测试替代隐式 if/else，降低认知负担
- [专用源与实时快照的口径可能不完全一致] → 统一 contract 只承诺公共字段，不强求所有扩展信息完全对齐
