## Context

当前工程已经完成多轮围绕 `market-summary`、财经数据 contract、CLI 模块化和服务拆分的重构，主流程与测试也具备基本形态，但仍有几处跨模块偏差没有真正收口：

- `market-summary` 在历史交易日缓存未命中或 `--force` 时，会直接调用只面向“当前市场”的行情抓取逻辑，导致目标交易日与实际行情日期脱钩。
- 交易日判断复用了通用“工作日”语义，而不是更保守的 A 股交易日语义，调休周末会被误判为交易日。
- 新闻聚合层已经切到从本地库读取财联社电报和看盘数据，但采集入库链路未接通，导致总结常年读取空数据源。
- CLI 已拆分为模块包，但没有保住 `python -m src.cli` 入口，说明模块化改造只完成了导入侧，没有完成执行入口闭环。

这些问题不是单点 bug，而是“规格契约已经声明，多个模块各自实现了一半”的典型状态。如果不集中治理，后续缓存、测试和总结内容会继续彼此掩盖问题。

## Goals / Non-Goals

**Goals:**
- 让 `market-summary` 的目标交易日、实际市场数据、缓存键和值保持同一语义。
- 用可解释、保守的 A 股交易日规则替换当前泛化工作日判断。
- 让财联社电报和看盘数据形成“抓取/解析 -> 入库 -> 聚合消费”的闭环。
- 恢复模块化 CLI 的双入口兼容性，并用测试显式锁住。
- 为上述行为补充直接面向规格语义的测试，而不是只验证当前实现细节。

**Non-Goals:**
- 不在本次变更中引入新的外部财经数据源。
- 不扩展市场总结模板内容，只修正输入语义和数据来源。
- 不对数据库表结构做大规模迁移，除非实现阶段发现现有字段无法表达既有数据。
- 不重做整个 CLI 组织结构，只补足入口兼容层和对应回归测试。

## Decisions

### 1. 历史交易日总结禁止使用“当前行情 API”作为隐式回退

`MarketAnalyzer.collect_market_data()` 需要区分两类场景：

- 目标日期等于当前可用交易日：可以继续使用现有实时抓取能力
- 目标日期早于当前可用交易日：只能使用该日期缓存，或调用明确支持目标日期的历史数据抓取路径

如果暂时没有完整的历史行情 API，就必须把“历史日期无缓存”的结果暴露为明确失败或不可用状态，而不是把 today 数据写入目标日期缓存。

选择理由：
- 规格要求的是“目标交易日一致性”，不是“尽量返回一些数据”
- 错误地缓存 today 数据会污染后续所有离线和缓存命中场景，比显式失败更难排查

备选方案：
- 继续沿用 today 数据兜底，并在输出里提示“近似数据”。放弃原因：会破坏缓存可信度，且与现有 OpenSpec 语义冲突。

### 2. 交易日判断采用“周一到周五且非法定节假日”的保守规则

当前 `chinese_calendar.is_workday()` 适合通用上班日判断，不适合证券交易日判断。本次改为在 `MarketAnalyzer` 内部统一封装更保守的 A 股规则：

- 周末一律不是交易日
- 法定节假日不是交易日
- 不把调休周末视为交易日

默认交易日选择、上一篇/下一篇交易日推导、文章窗口计算都使用同一套规则。

选择理由：
- 现有基线 spec 明确写的是“排除周末和法定节假日”
- 该规则虽然不等价于交易所正式日历，但比通用工作日更贴近当前规格，也更符合已有测试和用户认知

备选方案：
- 接入完整交易所日历源。放弃原因：当前没有稳定依赖和现成表结构，超出本次收口范围。

### 3. 相关文章窗口切换为显式的交易日边界，而不是回溯 N 个交易日整天范围

相关文章选择需要从“最近 3 个交易日”改成精确窗口，至少满足以下约束：

- 窗口由目标交易日和下一个交易日推导
- 查询条件和 CLI 展示使用同一个窗口对象
- 结果返回中携带实际窗口，用于日志和测试验证

窗口边界遵循当前基线 spec：`trade_date 15:00` 到 `next_trading_date 09:15`。

选择理由：
- 当前 `trade_days_back=3` 只是从“自然天回退”升级到“交易日回退”，但仍然不满足精确窗口要求
- CLI 若展示的是推导窗口，查询却用另一套逻辑，会继续制造不可解释结果

备选方案：
- 继续保留回溯 N 个交易日，只优化显示。放弃原因：只能改善可见性，不能解决筛选语义不一致。

### 4. 财联社新闻改为“入库优先、聚合只读”的闭环

`collect_news_data()` 保持只消费本地服务，但必须新增稳定的新闻采集入口来填充本地表：

- 电报：通过 `CLSRollClient` 拉取后统一保存到 `cls_telegraphs`
- 看盘：通过 `CLSWatchClient` 拉取后统一保存到 `cls_watch_data`
- 市场总结阶段只调用服务层查询，不直接混用远端原始响应

这让总结流程在在线和离线模式下都只面对一种新闻数据契约。

选择理由：
- 聚合层直接混用远端和本地数据会再次引入 contract 漂移
- 本地入库后才能稳定支持离线总结、重复生成和可审计测试

备选方案：
- 在 `market-summary` 执行时临时在线拉取财联社数据。放弃原因：会削弱离线语义，也无法形成稳定缓存。

### 5. CLI 兼容性通过显式 `__main__` 入口修复，而不是依赖包导入副作用

模块化后 `src.cli` 已成为包，因此 `python -m src.cli` 需要明确的 `src/cli/__main__.py`。本次保留：

- 安装脚本入口 `wchat = "src.cli:main"`
- 模块入口 `python -m src.cli`

二者最终都汇聚到同一 `main()`。

选择理由：
- 这是 Python 包执行模型的直接要求，最小且稳定
- 不需要回退模块化结构

备选方案：
- 删除 `src/cli/` 包，恢复单文件入口。放弃原因：会推翻已完成的模块化改造。

## Risks / Trade-offs

- [历史日期行情在无缓存时可能直接失败] → 通过 CLI 和日志明确提示“目标日期无可用市场数据”，避免产生错误缓存。
- [保守交易日规则仍不等于交易所完整日历] → 先满足当前 OpenSpec 基线；若后续需要更高精度，再单独提出交易所日历能力。
- [新闻入库闭环增加一条采集链路] → 将抓取、解析、入库职责分层，保持 `market-summary` 聚合层只读。
- [精确文章窗口可能导致现有测试样本数量变化] → 测试改为断言窗口边界和入选/排除规则，不依赖脆弱的文章总数。
- [CLI 入口修复后仍可能遗漏其它调用路径] → 增加 `python -m src.cli --help` 与 `python -m src.cli ai --help` 的回归测试。

## Migration Plan

1. 先修复 CLI 模块入口，使基本命令面在现有结构下稳定可执行。
2. 抽出统一的 A 股交易日判断与下一交易日推导逻辑，替换默认日期选择和文章窗口计算。
3. 收紧 `market-summary` 的历史日期市场数据策略，禁止 today 数据写入历史缓存。
4. 接入财联社电报与看盘数据的入库链路，再保持聚合层只读本地数据。
5. 最后补齐规格导向测试，覆盖历史日期、交易日边界、新闻闭环和 CLI 入口。

回滚策略：
- 若新闻入库链路引入不稳定，可暂时保留聚合只读接口并关闭自动采集入口。
- 若历史日期严格校验导致用户无法生成总结，可回滚到“显式失败但不写缓存”的中间状态，而不能回滚到 today 数据兜底。

## Open Questions

- 历史日期行情若仅部分数据源支持按日期查询，是否允许“部分历史数据 + 明确缺口”生成总结，还是必须整包失败；实现前需要按现有数据源能力确认。
- 财联社新闻入库触发方式是新增独立命令、复用现有服务启动脚本，还是由市场总结在线模式顺带刷新；需要结合当前运维方式定最终入口。
