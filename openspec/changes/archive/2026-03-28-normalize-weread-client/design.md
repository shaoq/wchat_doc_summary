## Context

`WeReadClient` 当前负责登录二维码、登录结果、公众号信息和文章列表四类请求，但其实现存在明显不一致：

- `get_login_result()` 没有走通用 `_request()` 封装，而是单独创建 `httpx.AsyncClient`
- 登录结果接口既承担 HTTP 请求，又承担状态解释，导致错误处理与其他接口风格不同
- `AuthService` 对登录结果结构有隐式假设，而测试却通过 mock `_request()` 来替代真实路径
- 公众号信息与文章列表接口已经做了字段归一化，但登录结果契约仍然是半原始响应、半业务语义混合

本次变更聚焦统一微信读书代理客户端本身，使认证与抓取服务能建立在稳定契约上。

## Goals / Non-Goals

**Goals:**
- 统一 `WeReadClient` 的请求入口与基础错误处理
- 为登录二维码、登录结果、公众号信息和文章列表定义稳定的返回结构
- 让 `AuthService` 基于显式契约而不是隐式字段猜测工作
- 让测试 mock 点与真实生产调用路径一致

**Non-Goals:**
- 不更换微信读书代理 API
- 不在本次变更中重构 `AuthService` 的数据库存储模型
- 不修改抓取服务的业务编排逻辑，除非为适配新客户端契约必须调整

## Decisions

### 1. 所有 WeReadClient 接口统一走请求封装路径

`WeReadClient` 的公开方法都必须通过同一套请求封装完成网络调用。特殊接口可以在收到原始响应后做状态归一化，但不再自行绕过 `_request()` 发请求。

备选方案：
- 保留 `get_login_result()` 的特例实现。放弃原因：会继续导致测试与实现路径分叉。

### 2. 客户端负责“传输层 + 轻度字段归一化”，业务语义由服务层解释

客户端负责：
- 发请求
- 处理网络与 HTTP 错误
- 归一化已知字段名差异

服务层负责：
- 决定“waiting / expired / success”这些业务状态如何驱动登录流程
- 决定 token 如何持久化

这能避免客户端既是 transport layer 又是完整业务层。

备选方案：
- 在客户端中完全解释登录业务状态。放弃原因：会让客户端继续膨胀，且难以复用于其他服务。

### 3. 登录结果返回结构标准化

登录结果接口应返回统一字典，保证调用方至少可以稳定读取：

- `status`
- `message`
- `token`
- `user_info`

这样 `AuthService` 和测试都不需要再猜测原始响应里是否有非标准字段。

备选方案：
- 直接透传原始 API body。放弃原因：上层会继续散落大量字段兼容逻辑。

## Risks / Trade-offs

- [登录接口的 HTTP 500 状态兼容处理被改坏] → 用单元测试覆盖 waiting、expired、success 和 request error 四类场景
- [客户端归一化过度，掩盖了上游异常] → 保留原始 message 信息并在日志中记录
- [AuthService 依赖旧结构] → 在改客户端契约时同步调整认证服务消费逻辑

## Migration Plan

1. 为 `WeReadClient` 定义统一返回契约
2. 重构 `get_login_result()` 走统一请求封装
3. 调整 `AuthService` 消费登录结果的逻辑
4. 更新 API 层与服务层测试，确保 mock 点与真实路径一致

回滚策略：
- 若登录接口兼容性出现问题，可暂时回退到旧的 `get_login_result()` 实现，但保留已梳理出的测试用例与契约说明

## Open Questions

- `_request()` 是否需要支持“允许特定 HTTP 状态码透传”这一能力，以便更自然处理登录轮询类接口
- 登录结果中的 `user_info` 是否需要进一步标准化字段名，还是只要求原样透传并保证存在性
