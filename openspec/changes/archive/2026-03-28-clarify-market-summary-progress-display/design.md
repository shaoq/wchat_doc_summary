## Context

当前 `market-summary` 的 CLI 已经有三阶段执行提示，但用户最终在终端中看到的主要是若干结论行和细项摘要，而不是稳定的阶段块。阶段标题更多只存在于运行时 spinner 文案里，执行完成后难以回看；同时市场数据来源、执行模式和“AI 生成之后是否已经保存完成”等关键信息没有被明确表达。

这次改动不需要调整底层数据采集或 AI 处理逻辑，重点是把现有执行过程重新组织成更清楚的可读输出，让用户在成功、离线和失败路径上都能快速理解“当前处于哪一阶段、用了什么数据、是否已经完成落盘”。

## Goals / Non-Goals

**Goals:**
- 让 `market-summary` 的输出形成稳定的三阶段块结构。
- 在命令开头明确展示交易日、执行模式和市场数据策略。
- 在阶段 1 明确展示市场数据来源语义，如 API、缓存、离线或强制刷新。
- 在阶段 3 将“生成”和“保存”闭合为一个用户可感知的完成态。
- 用 CLI 流程测试锁住输出结构，避免后续回退到散乱提示。

**Non-Goals:**
- 不重构 `MarketAnalyzer`、`AIProcessor` 或底层抓取逻辑。
- 不引入新的终端交互模式或复杂实时进度条。
- 不改变 `market-summary` 的命令参数和业务流程顺序。

## Decisions

### 1. 采用“持久阶段块”而不是继续依赖 transient spinner 文案

选择：每个阶段都要留下可回看的标题、结论和关键细节，执行结束后的 transcript 仍然能看出完整流程。

理由：
- 当前用户感知问题主要来自“执行完只剩几条摘要，不知道它们属于哪个阶段”。
- CLI transcript 的可回看性比运行时动画更重要。

备选方案：
- 保持现有 spinner 文案，只补更多摘要行。问题是结构层级仍然不稳定。
- 改成 Rich `Progress` 多任务进度条。问题是三个阶段都不是可度量进度，视觉上会更热闹但未必更清楚。

### 2. 增加命令级“执行上下文”行

选择：在阶段开始前显式输出交易日、执行模式和市场数据策略。

理由：
- 用户最关心的前置语义不是“程序开始跑了”，而是“这次到底按什么规则跑”。
- `--offline`、`--force`、缓存命中等语义若只埋在阶段细项里，理解成本高。

备选方案：
- 只在阶段 1 展示这些信息。问题是上下文分散，不利于开头快速定调。

### 3. 第 3 阶段改为“生成并保存市场总结”

选择：将 AI 生成耗时和输出文件位置都纳入第 3 阶段结论块，而不是在阶段外再追加一条“已保存到 ...”。

理由：
- 从用户角度，命令“完成”的标准不是模型返回文本，而是总结已经保存可用。
- 这能消除“显示生成完成后命令还在继续跑”的割裂感。

备选方案：
- 保留现有“生成完成”后单独输出保存路径。问题是完成态不闭合。

### 4. 用结构测试替代文案偶然性

选择：测试重点放在块结构、来源提示、阶段顺序和保存闭环，不只检查几个关键词存在。

理由：
- 当前测试只锁住“有输出”，但没有锁住“输出是否清楚”。
- 如果不收紧结构测试，后续很容易再次退化成散行日志。

## Risks / Trade-offs

- [输出行数增加，终端更长] → 控制每阶段只展示关键语义，避免把所有内部细节都打出来。
- [文案收紧后现有测试会大量改动] → 以结构稳定为优先，测试同步改为验证阶段块和关键字段。
- [执行上下文与阶段细项可能出现语义重复] → 上下文只讲“这次怎么跑”，阶段细项只讲“这一阶段结果如何”。
