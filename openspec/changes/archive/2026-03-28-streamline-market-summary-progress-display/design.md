## Context

`market-summary` 的核心执行链路已经比较完整，但 CLI 进展展示还是由 `console.status()` 和多段 `console.print()` 手动拼接完成。当前输出存在几个直接问题：

- 阶段标题、阶段结果和补充信息之间的组织关系不稳定，成功路径与失败路径的可读性差异很大。
- 行情摘要、资料来源统计、时间窗口都由零散打印语句输出，顺序和分组语义依赖调用位置，不利于后续继续演进。
- 测试目前主要覆盖命令是否停止、参数是否透传，对输出结构本身约束较弱，因此“看起来乱”的回归很容易再次发生。

这个改动集中在 CLI 呈现层，不涉及 `MarketAnalyzer`、`AIProcessor` 或底层数据契约的重新设计。

## Goals / Non-Goals

**Goals:**
- 为 `market-summary` 定义结构稳定的三阶段进展输出。
- 让阶段 1、阶段 2 的摘要都使用统一的成功 / 空结果 / 失败呈现模式。
- 让资料统计和时间窗口按固定顺序展示，降低用户扫描成本。
- 为关键输出顺序和关键文案增加 CLI 回归测试。

**Non-Goals:**
- 不改变市场数据、新闻资料或 AI 生成本身的业务逻辑。
- 不引入新的终端依赖或复杂的实时动态界面。
- 不把 `market-summary` 改造成逐条资料流式更新的交互式命令。

## Decisions

### 1. 用统一的阶段渲染辅助逻辑收敛输出，而不是继续在命令函数中散落 `console.print`

把阶段头、结果图标、摘要行和阶段结束后的补充信息收敛到一组小型辅助函数或局部渲染逻辑中，让每个阶段都遵循同一套输出骨架。

这样做的原因是：当前“乱”并不是数据不够，而是呈现结构没有被抽象出来。只要结构继续散落在命令主体里，后续每次补一行提示都可能再次破坏布局。

备选方案：继续在 `market-summary` 命令里手写输出顺序。
拒绝原因：实现成本最低，但无法形成稳定约束，后续维护仍然脆弱。

### 2. 每个阶段都采用“阶段头 + 阶段结论 + 细项摘要”的固定结构

阶段头仍保留 `[1/3]`、`[2/3]`、`[3/3]` 这样的明确编号；阶段完成后，立即输出该阶段的结论，再输出与该阶段相关的细项摘要。

推荐结构是：
- 阶段头负责说明“正在做什么”
- 阶段结论负责说明“成功 / 空结果 / 失败”
- 细项摘要负责说明“具体拿到了什么”

这样用户在终端里自上而下阅读时，不需要在多段空行和零散提示之间自己拼装语义。

备选方案：改用 Rich `Progress` / `Live` 组件持续刷新。
拒绝原因：`market-summary` 只有 3 个粗粒度阶段，动态刷新收益有限，反而更容易引入闪烁和测试不稳定。

### 3. 新闻资料阶段采用固定来源顺序，并把时间窗口视为同一阶段的补充摘要

阶段 2 统一按“财联社电报 -> 看盘数据 -> 相关文章”的顺序展示来源状态与数量，再在同一阶段下展示“看盘 -> 电报 -> 文章”的时间窗口信息。即使某个来源为空或某个窗口缺失，也保持整体顺序不变，只省略缺失项本身，不插入无意义空白。

这样做有两个目的：
- 用户多次执行命令时，可以快速横向比较同一来源的差异。
- 测试可以稳定断言输出顺序，而不是依赖宽松的关键词存在判断。

备选方案：沿用当前“先打印来源统计，再无条件打印所有窗口行”的方式。
拒绝原因：在空资料或部分缺失场景下，终端会留下很多缺乏上下文的内容，读起来仍然松散。

### 4. 提前失败时，输出必须在当前阶段内闭合

如果阶段 1 因市场数据不可用而停止，CLI 必须在阶段 1 区块内给出明确失败结论，然后直接返回，不再进入阶段 2 和阶段 3 的标题展示。这样失败路径与成功路径共享同一套结构，只是终止得更早。

备选方案：保留当前“打印一条错误信息然后 return”。
拒绝原因：行为虽然正确，但终端上下文不足，用户不容易判断命令是异常中断还是按预期 fail-fast。

### 5. 测试覆盖输出结构中的顺序和关键结论，而不是逐字符锁定整段富文本

CLI 测试应断言：
- 三个阶段标题在成功路径中按顺序出现
- 市场数据失败时不出现后续阶段标题
- 新闻来源和时间窗口按约定顺序出现
- 离线模式下仍能看到清晰的离线语义

不建议把 Rich 标记、缩进空格数或完整多行文本完全写死，否则会让 CLI 文案微调变得过于昂贵。

## Risks / Trade-offs

- [输出结构测试过于脆弱] -> 只锁定阶段顺序、关键文案和是否提前停止，不锁死全部空白字符与样式标签。
- [为了紧凑而丢掉有价值的上下文] -> 保留来源数量、时间窗口、数据来源和失败原因这些排障关键信息。
- [辅助渲染逻辑仍然局限在单个命令中] -> 优先保持实现简单；如果后续更多命令出现相同需求，再抽到共享 CLI 工具层。

## Migration Plan

这是纯 CLI 呈现层变更，无需数据迁移。实现时直接替换现有 `market-summary` 进展输出，并通过现有 CLI 测试套件验证行为。
