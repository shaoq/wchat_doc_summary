## Context

`FetcherService` 是当前公众号抓取主链路的编排核心，负责从微信读书代理获取文章列表、抓取原文、保存入库并驱动部分时间过滤逻辑。但现状存在几类问题：

- 同一文件中存在重复定义的方法，且其中一个方法名与职责明显不符
- 全量抓取、增量抓取、公众号信息解析和发布时间回填没有稳定边界
- 时间过滤与提前停止翻页逻辑存在错误，导致“抓最近 N 天文章”不可靠
- 发布时间回填逻辑混用了 `mp_id` 与 `feed.id`，并在会话生命周期结束后继续操作 session
- 现有测试主要覆盖 mock 路径，难以验证真实抓取行为

这次变更聚焦 `FetcherService` 本身，不扩展新的抓取功能，而是把现有能力收敛成可维护、可验证、可复用的结构。

## Goals / Non-Goals

**Goals:**
- 明确 `FetcherService` 的公开方法边界，恢复方法名与职责一致
- 让全量抓取、增量抓取、公众号信息解析和发布时间回填分别可测试
- 修复最近 N 天抓取的时间过滤与翻页停止规则
- 修复发布时间回填中的参数语义和 session 生命周期错误
- 统一抓取服务的异常处理和返回行为，降低 CLI 对历史残留逻辑的依赖

**Non-Goals:**
- 不替换微信读书代理 API
- 不重构 `Article` 或 `Feed` 数据模型
- 不在本次变更中设计新的抓取调度机制
- 不修改文章正文抓取与 HTML 解析实现，除非为修复抓取流程必须调整接口

## Decisions

### 1. 公开接口固定为五个方法

`FetcherService` 的公开接口收敛为：

- `fetch_feed(mp_id, ...)`
- `fetch_all(...)`
- `fetch_incremental(mp_id, ...)`
- `get_mp_info_from_article(article_url)`
- `backfill_publish_time(mp_id)`

其余逻辑全部下沉为私有辅助方法，避免重复定义与职责串味。

备选方案：
- 保留当前结构，仅修正局部 bug。放弃原因：方法覆盖和职责错位会持续制造隐性问题。

### 2. 全量抓取和增量抓取共享同一套文章保存路径

文章抓取、去重、原文抓取、HTML 解析和入库保存统一复用 `_fetch_and_save_article()` 及相关私有辅助函数。全量与增量只在“文章列表选择策略”和“停止条件”上不同。

备选方案：
- 为增量抓取单独复制一套保存流程。放弃原因：重复逻辑会再次导致分叉行为。

### 3. 时间过滤以“是否早于 cutoff”为唯一判定依据

最近 N 天抓取只依赖统一的发布时间解析函数与 cutoff 时间比较：

- 发布时间缺失的文章不作为提前停止翻页依据
- 若当前页所有可解析发布时间的文章都早于 cutoff，才允许停止继续翻页
- 单篇文章只要发布时间早于 cutoff，就跳过，不入库

这样可以避免当前实现中 `all_older` 分支恒为 `False` 的问题。

备选方案：
- 继续依赖“API 返回顺序一定严格新到旧”的隐式假设。放弃原因：该假设未被契约保证，且当前代码已因此出错。

### 4. 发布时间回填统一以 `mp_id` 作为外部入口参数

`backfill_publish_time()` 对外统一接受 `mp_id`，内部自行解析 `Feed`。这与 CLI 和服务层的其他调用语义保持一致，并避免混用 `feed.id` 与 `mp_id`。

回填更新必须在有效 session 范围内完成，禁止在上下文退出后继续 `flush` 或写对象。

备选方案：
- 将回填入口改成 `feed_id`。放弃原因：会增加调用方转换成本，且与现有服务接口风格不一致。

### 5. 增量抓取语义明确定义为“只抓取晚于库内最新文章时间的文章”

`fetch_incremental()` 的停止条件基于数据库内该订阅已存在的最新文章发布时间：

- 若 API 返回文章时间晚于最新时间，则继续抓取并保存
- 一旦遇到不晚于最新时间的文章，可停止当前及后续页抓取
- 对缺失发布时间的文章采取保守策略：不作为停止依据，但允许进入后续保存与回填流程

备选方案：
- 基于 article_id 做字符串比较或仅依赖去重。放弃原因：不能表达时间语义，也无法减少不必要翻页。

## Risks / Trade-offs

- [发布时间缺失较多时，增量抓取停止条件会变弱] → 对缺失时间文章采取保守策略，并依赖后续回填补齐
- [修复抓取逻辑后，实际抓取数量可能与旧版本不同] → 在测试和日志中显式记录 cutoff、跳过数量和停止原因
- [统一接口后可能暴露 CLI 依赖旧行为的问题] → 在实施时同步调整 `wchat fetch` 和 `wchat subscribe` 调用路径
- [回填流程仍依赖外部 API 列表字段完整性] → 将回填视为最佳努力流程，不阻断主抓取成功返回

## Migration Plan

1. 清理 `FetcherService` 中的重复定义和错误命名
2. 重构全量抓取与增量抓取为共享保存路径
3. 修复最近 N 天抓取过滤和停止条件
4. 重写 `backfill_publish_time()` 的参数与 session 生命周期
5. 调整 CLI 调用点并补测试

回滚策略：
- 若增量抓取新逻辑不稳定，可保留全量抓取与公众号信息解析修复，单独回退增量抓取入口
- 若回填逻辑引发问题，可暂时保留“主抓取成功、回填降级为日志告警”的模式

## Open Questions

- 当 API 返回整页文章都缺失发布时间时，最近 N 天抓取是否需要额外的最大页数保护以避免无效翻页
- 是否需要将 `fetch_incremental()` 暴露为独立 CLI 命令，还是仅保留为服务层能力供后续调度复用
