## Context

`market-summary` 的主要业务链路已经具备完整形态，但执行层还存在几类边界不稳的问题：
- CLI 在解析 `--date` 之前就初始化 `AIProcessor`，本地参数错误可能被远端 AI 配置错误抢先打断。
- 新闻阶段会容忍单一来源失败继续执行，但 CLI 结论仍统一显示为“获取完成”，没有把退化语义显式表达出来。
- 总结保存目前先提交数据库、再写 Markdown 文件，一旦文件落盘失败，会留下“数据库有记录但文件不存在”的失配状态。
- 市场数据获取策略同时分布在 `MarketAnalyzer.collect_market_data()` 和 `MarketDataCacheService.get_market_data()`，主链路与辅助入口容易产生漂移。

这些问题单看都不大，但都落在 `market-summary` 的用户可见边界上。它们会让命令在错误场景下不够可预测，也让后续继续迭代 CLI 展示和缓存策略时更难维护。

## Goals / Non-Goals

**Goals:**
- 保证 `market-summary` 的本地前置校验先于 AI 依赖初始化执行。
- 让新闻阶段能区分“完全成功”和“部分退化但继续执行”。
- 明确总结保存的完成语义，降低数据库和文件落盘失配风险。
- 收敛市场数据策略入口，减少重复实现。
- 用流程测试锁住上述执行语义。

**Non-Goals:**
- 不改动 `market-summary` 的核心业务阶段顺序。
- 不重构 `AIProcessor` 的 prompt 结构或模板内容。
- 不引入新的存储介质或事务中间件。

## Decisions

### 1. CLI 前置校验必须先于 `AIProcessor` 初始化

选择：将日期解析、`--list` 分支和其他纯本地前置判断放在 `AIProcessor` 初始化之前。

理由：
- 这类错误应由本地逻辑直接返回，不能依赖 LLM 配置是否正确。
- 这能让 CLI 错误来源更可解释，也减少无意义的 AI 初始化开销。

备选方案：
- 保持当前结构，仅在初始化失败时包一层更友好的报错。缺点是错误因果顺序仍然是错的。

### 2. 新闻阶段使用“成功 / 退化 / 失败”三态，而不是单一成功结论

选择：`collect_news_data()` 继续允许单一来源失败后降级运行，但 CLI 和返回结构要显式表达是否存在 error 来源。

理由：
- 现有设计本身允许缺一源继续生成，这没有问题；问题是 CLI 需要把这种“带缺口的成功”讲清楚。
- 这样既不影响可用性，也能提升结果解释性。

备选方案：
- 任一新闻源失败就中断整个命令。缺点是过于保守，会降低可用性。

### 3. 总结保存采用“文件成功后再完成整体成功态”语义

选择：把“命令完成”定义为数据库记录与 Markdown 文件都可用；实现上优先保证两者尽量同步，并在文件写入失败时避免静默留下完成态。

理由：
- 对用户来说，总结是否真正完成，取决于最终文件是否可用。
- 当前数据库先提交再写文件，容易产生“列表里能看到记录，但磁盘没有内容”的残缺状态。

备选方案：
- 维持现状，仅在文件写入失败时打印日志。缺点是用户可见状态仍然不一致。

### 4. 市场数据策略入口以 `MarketAnalyzer.collect_market_data()` 为主，避免双轨语义

选择：保持 `market-summary` 主链路只通过 `MarketAnalyzer.collect_market_data()` 表达缓存/强刷/离线策略，并让其他辅助入口围绕它收敛，而不是平行演化。

理由：
- 当前 `market-summary` 真实语义已经主要集中在 `MarketAnalyzer`，这是更合适的编排层。
- 减少重复逻辑有助于避免后续“一个入口改了，另一个入口没改”。

备选方案：
- 把主链路切回 `MarketDataCacheService.get_market_data()`。缺点是会把历史交易日和离线等上层语义再次下沉，改动更大。

## Risks / Trade-offs

- [保存一致性处理可能引入更复杂的错误分支] → 明确“数据库/文件都成功才算完成”，并用测试锁住失败路径。
- [新闻阶段三态会让 CLI 文案更复杂] → 保持状态只有成功、退化、失败三种，避免引入更多细分状态。
- [收敛市场数据入口时可能影响现有测试假设] → 以流程测试为主，优先验证用户可见行为而非内部调用细节。
